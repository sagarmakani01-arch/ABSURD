# ABSURD Tool System

The Tool System manages the lifecycle of tools: what exists, how new tools come into existence, and how they are executed safely. Consists of the **Registry**, **Tool Generator**, **Security Sandbox**, and **Tool Execution**.

```
Registry ◄───────── (registered tools)
   │
   ▼                            ┌──────────────────┐
 Capability Detector            │ TOOL GENERATOR   │
   │ (gap_spec)                 └────────┬─────────┘
   ▼                                    │
 Registry (reserve id) ────────────────►│
                                        ▼
                                ┌──────────────────┐
                                │ SECURITY SANDBOX │
                                └────────┬─────────┘
                                         ▼
                                ┌──────────────────┐
                                │ TOOL EXECUTION   │
                                └──────────────────┘
```

## 1. Tool Registry

- Single source of truth for existing tools (persisted in Tool Memory; in-memory cache for hot path).
- Each tool record:

```json
{
  "tool_id": "tool_01H...",
  "name": "csv_to_markdown_table",
  "description": "Converts CSV text/URL into a Markdown table.",
  "input_schema": {"type": "object", "properties": {...}},
  "output_schema": {"type": "object", "properties": {...}},
  "provenance": "generated" | "manual",
  "status": "active" | "disabled" | "quarantined",
  "confidence": 0.92,
  "usage_count": 14,
  "success_rate": 0.85,
  "tags": ["format", "csv"],
  "created_at": "...",
  "source_task_id": "task_01G..."        // for generated tools
}
```

- Operations: `list`, `get`, `register`, `disable`, `quarantine`, `metadata update` (confidence/success_rate maintained by the Evolution Loop).

## 2. Tool Generator

- Triggered by a `gap_spec` from the Capability Detector: `{name_hint, description, input_schema, output_schema, security_constraints}`.
- Produces a candidate tool: typed function/class implementation plus metadata.
- Strategies:
  1. **Template-based** — deterministic code generation from schemas (no LLM): handles parse/transform/format tools reliably.
  2. **LLM-assisted** — freeform tools generated by an LLM, subject to the same schema and sandbox validation.
- Every generated candidate must pass **static schema validation** (input/output JSON Schema conformance) before touching the sandbox.
- Generation is idempotent: the Registry is checked first, so a gap is never generated twice concurrently (registry-level lock on `name_hint`).

## 3. Security Sandbox

Non-negotiable gate before any generated tool executes.

- **Isolation:** each execution runs in a fresh subprocess (or container, configurable) with:
  - Network disabled by default; enable-only via explicit allow-listed domains from `security_constraints`.
  - No access to host filesystem except a read-only scratch dir; writes allowed only to the scratch dir.
  - Dedicated low-privilege OS user (no admin, no shell inherit).
- **Resource limits:** CPU seconds, peak memory, wall-clock timeout (default 30s), output size cap.
- **Static analysis pre-run:** AST inspection rejecting: `eval`/`exec`, `subprocess`/`os.system`, file-path escapes (`..`), imports outside an allow-list, obvious infinite loops.
- **Result handling:** stdout/return value must deserialize against `output_schema`, else the run is marked `invalid_output` (a failure class the Evolution Loop understands).
- **Secrets:** tools receive only the inputs passed by the caller; no environment or credential injection by defaults.

## 4. Tool Execution

- Sync path (FastAPI-style call) for fast tools; async/worker path for long-running tool execution, with `tool.executing` WS events.
- Execution result record (the contract consumed by the Evolution Loop):

```json
{
  "task_id": "...",
  "tool_id": "...",
  "status": "success" | "failure" | "invalid_output" | "violation" | "timeout",
  "result": {...},
  "error": {"kind": "runtime_error|schema_violation|sandbox_violation|timeout", "message": "..."},
  "duration_ms": 1234,
  "traces": ["..."]       // sanitized logs/stack
}
```

- Retries: idempotent tools may auto-retry once on transient failures (`timeout`); non-idempotent tools never auto-retry.
- Every execution result is persisted to Experience Memory and emitted as an event for the Evolution Loop.

## 5. Failure Classification

Used by `Analyze` in the Evolution Loop:

| Failure kind | Meaning | Likely evolution action |
|---|---|---|
| `runtime_error` | Code threw during execution | Fix implementation, regenerate candidate |
| `schema_violation` | Input/output didn't match schema | Fix schema, validation pre-check |
| `sandbox_violation` | Tool tried disallowed op | Patch constraints or discard tool |
| `timeout` | Exceeded resource limit | Optimize, raise limit within policy |
| `unfillable_gap` | No tool could be generated for the step | Record capability gap knowledge graph node |
