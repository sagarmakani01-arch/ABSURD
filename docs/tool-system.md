# ABSURD Tool System

> **Status note (Phase 13):** the Tool Generator implements the deterministic
> **template** strategy for real and the **LLM** strategy when
> `ABSURD_LLM_BASE_URL`/`ABSURD_LLM_API_TOKEN`/`ABSURD_LLM_MODEL` are
> configured (falling back to the template with a logged event otherwise).
> The **security sandbox** runs tool code for real — AST policy-gated
> subprocess execution — and the **behavioral gate** executes a tool's stored
> tests during evaluation. See §2–§4 below.

The Tool System manages the lifecycle of tools: what exists, how new tools come into existence, and how they are executed safely. Consists of the **Registry**, **Tool Generator**, **Security Sandbox**, and **Tool Execution**.

```
Registry ◄───────── (registered tools)
   │
   ▼                            ┌──────────────────┐
 Capability Detector            │ TOOL GENERATOR   │
   │ (gap_spec)                 └────────┬─────────┘
   ▼                                    │
 Registry (reserve id) ────────────────►│
                                        ▼
                                ┌──────────────────┐
                                │ SECURITY SANDBOX │
                                └────────┬─────────┘
                                         ▼
                                ┌──────────────────┐
                                │ TOOL EXECUTION   │
                                └──────────────────┘
```

## 1. Tool Registry

- Single source of truth for existing tools (persisted in Tool Memory; in-memory cache for hot path).
- Each tool record:

```json
{
  "tool_id": "tool_01H...",
  "name": "csv_to_markdown_table",
  "description": "Converts CSV text/URL into a Markdown table.",
  "input_schema": {"type": "object", "properties": {...}},
  "output_schema": {"type": "object", "properties": {...}},
  "provenance": "generated" | "manual",
  "status": "active" | "disabled" | "quarantined",
  "confidence": 0.92,
  "usage_count": 14,
  "success_rate": 0.85,
  "tags": ["format", "csv"],
  "created_at": "...",
  "source_task_id": "task_01G..."        // for generated tools
}
```

- Operations: `list`, `get`, `register`, `disable`, `quarantine`, `metadata update` (confidence/success_rate maintained by the Evolution Loop).

## 2. Tool Generator

- Triggered by a `gap_spec` from the Capability Detector: `{name_hint, description, input_schema, output_schema, security_constraints}`.
- Produces a candidate tool: typed function/class implementation plus metadata.
- Strategies:
  1. **Template-based** — deterministic code generation from schemas (no LLM): handles parse/transform/format tools reliably. **Implemented as of Phase 12**: `backend/app/services/generator.py` scaffolds a valid-Python validate-and-echo candidate; the capability detector auto-generates DRAFT candidates for gap/partial steps during task runs, and `POST /api/v1/tools/generate` triggers it explicitly. Generation is idempotent per capability slug (a capability is never generated twice).
  2. **LLM-assisted** — freeform tools generated by an LLM (OpenAI-compatible
     chat completions), subject to the same schema, AST-policy and sandbox
     validation. **Implemented as of Phase 13d** — `backend/app/services/llm.py`;
     active when `ABSURD_LLM_*` is configured, otherwise `generation_available`
     reports only the template strategy and generation stays deterministic.
- Every generated candidate must pass **static schema validation** (input/output JSON Schema conformance) before touching the sandbox.
- Generation is idempotent: the Registry is checked first, so a gap is never generated twice concurrently (registry-level lock on `name_hint`).

## 3. Security Sandbox

Non-negotiable gate before any tool executes. **Implemented** in
`backend/app/services/sandbox.py` (`check_policy`, `ToolSandbox.execute`,
`ToolSandbox.run_tests`):

- **Static analysis pre-run (AST policy):** `check_policy` rejects any source
  containing `eval`/`exec`/`compile`/`__import__`, *all* `import` statements,
  `open`, file-path tricks, and attribute access on dunders or `__class__`
  chains. The policy gates tool **source and stored tests** at registration
  time *and* again before every execution, so a stored test can never smuggle
  privileged operations into a runtime run.
- **Isolation:** each execution runs in a fresh `python -I` (isolated-mode)
  subprocess with a throwaway working directory. No network access, no
  environment inheritance, no filesystem access beyond the scratch dir the
  runner itself creates. Tool code is never imported or evaluated in the
  gateway process.
- **Resource limits:** wall-clock timeout (default 30s, per request
  configurable via `timeout_seconds`) and an output-size cap; a timed-out run
  is marked `TIMEOUT`.
- **Result handling:** stdout must deserialize to a JSON value matching the
  tool's `input_schema`/`output_schema` contract; mismatches and exceptions
  are recorded as `FAILED` with a machine-readable `code`, subprocess exit
  codes are propagated (a crashed tool leaves a real `code` behind), and
  output above the cap or deserialization failure is marked `FAILED`.
- **Records:** every run writes an `ExecutionRecord` (task/tool ids, status,
  inputs, output/error, duration) and emits `TOOL_EXECUTION_STARTED/`
  `TOOL_EXECUTION_FINISHED` events carrying the result `code`. The Evolution
  Loop consumes these for quarantine and revisions.
- **Behavioral gate:** `ToolSandbox.run_tests(tool)` executes the tool's own
  stored test fragments (policy-checked) end-to-end in one subprocess and
  reports per-test pass/fail — this powers `POST /evaluations`.
- **Secrets:** tools receive only the inputs passed by the caller; no
  environment or credential injection by defaults.

## 4. Tool Execution

**Implemented** (Phase 13a–13b). The Agent Engine executes each step of a
covered plan through the sandbox (`backend/app/core/agent/engine.py`,
`_execute_steps`) with inputs resolved positionally from the task context;
results accumulate as `{step_id, tool_id, output}` and the task becomes
`COMPLETED` only if every step's output validated against the step's expected
output schema. Unregistered or quarantined tools surface as structured
outcomes (`TOOL_NOT_AVAILABLE`, `TOOL_EXECUTION_FAILED` with `code`), and
`POST /api/v1/tools/{id}/execute` exposes the same path on demand (422 for
tools that are not `REGISTERED`).

- Execution result record (persisted per run):

```json
{
  "task_id": "...",
  "tool_id": "...",
  "status": "COMPLETED" | "FAILED" | "TIMEOUT" | "SECURITY_REJECTED",
  "output": {...},
  "code": null | "runtime_error|schema_violation|sandbox_violation|timeout",
  "duration_ms": 1234
}
```

- Consecutive failed execution records (≥3) quarantine a tool —
  `DEPRECATED` — which then stops covering new steps; the next task asking
  for that capability fails `NO_CAPABILITY` and seeds a replacement DRAFT.
- Every execution result is persisted and emitted as an event for the
  Evolution Loop (real failure data, not simulation).

## 5. Failure Classification

Used by `Analyze` in the Evolution Loop:

| Failure kind | Meaning | Likely evolution action |
|---|---|---|
| `runtime_error` | Code threw during execution | Fix implementation, regenerate candidate |
| `schema_violation` | Input/output didn't match schema | Fix schema, validation pre-check |
| `sandbox_violation` | Tool tried disallowed op | Patch constraints or discard tool |
| `timeout` | Exceeded resource limit | Optimize, raise limit within policy |
| `unfillable_gap` | No tool could be generated for the step | Record capability gap knowledge graph node |
